# 智序 · Smart ERP 个人博客系统开发需求文档

**文档版本：** V1.0  
**项目名称：** 智序 · Smart ERP  
**产品定位：** 个人博客与内容管理系统  
**开发模式：** 在现有项目基础上持续迭代，不随意重构已有业务。

---

# 一、项目总体说明

## 1.1 项目定位

智序（Smart ERP）是一个个人博客与内容管理系统，主要用于个人技术文章发布、生活记录、个人展示以及访客互动。

系统由两个部分组成：

1. 前台门户：面向普通访客，负责文章阅读、个人展示、日记浏览和留言互动。
2. 后台管理：面向管理员，负责文章、分类、标签、留言、评论、日记、公告、友链、用户和系统配置管理。

产品口号：

> 让工作更智能，让每一天更有序。

本项目虽然名称中包含 ERP，但实际产品定位是个人内容管理平台，不应设计成传统企业 ERP 系统。

## 1.2 技术栈

当前项目技术基础：

| 技术 | 用途 |
|---|---|
| Java | 后端开发语言 |
| Spring Boot 2.7 | 后端框架 |
| Thymeleaf | 页面模板引擎 |
| MyBatis-Plus | ORM 与数据库操作 |
| MySQL | 数据库 |
| HTML / CSS / JavaScript | 前端页面 |
| Maven | 项目构建 |

开发前必须先检查项目实际使用的 JDK、依赖版本、数据库结构、已有 Controller、Service、Mapper、实体类和页面模板。

不得仅根据本文档推测项目中已经存在的代码或功能。

## 1.3 核心开发原则

1. 优先复用现有代码和项目结构。
2. 不随意修改已经正常运行的业务逻辑。
3. 不重复创建已有实体类、接口、工具类和页面。
4. 不擅自升级 Spring Boot、MyBatis-Plus 或 JDK 版本。
5. 不为了实现一个简单功能引入不必要的第三方框架。
6. 所有后台写操作必须经过服务端权限校验。
7. 前台展示数据必须来自真实数据库，不使用固定模拟数据。
8. 删除、审核、发布等操作必须有明确的成功和失败反馈。
9. 页面布局、按钮样式、表单样式和交互方式保持统一。
10. 每个开发阶段完成后进行编译、功能检查和回归测试。

   - 关于我

2. 个人介绍区域

# 四、后台管理详细需求

## 4.1 后台整体布局

采用经典后台管理布局：

- 左侧：系统 Logo、一级菜单、二级菜单。
- 顶部：页面标题、面包屑、通知入口、用户头像菜单。
- 右侧：页面内容区域。
- 页面底部：必要时展示版权信息。

### 视觉要求

1. 整体风格简洁、现代、专业。
2. 避免过度使用紫色，形成有辨识度的品牌配色。
3. 页面以浅色背景为主，内容区域层次清晰。
4. 卡片、表格、表单、弹窗样式统一。
5. 不要使用过多渐变、阴影和装饰性图形。
6. 按钮主次明确，危险操作采用独立的警示样式。
7. 页面间距、字号、圆角、边框统一。
8. 表格和表单优先考虑实际操作效率。

### 通用交互要求

所有列表页面尽可能统一以下结构：

1. 页面标题和简短说明。
2. 查询条件区域。
3. 操作按钮区域。
4. 数据表格。
5. 分页区域。

所有表单页面统一：

- 必填项标识
- 字段校验
- 错误提示
- 保存按钮
- 取消按钮
- 提交中的加载状态

所有删除操作必须：

- 显示二次确认。
- 明确展示将删除的对象。
- 说明是否存在关联数据。
- 防止重复提交。
- 处理删除失败。
- 不允许未经确认直接删除。

## 4.5 标签管理

### 页面布局

推荐使用左侧分类列表、右侧标签列表的两栏布局。

左侧：

### 标签字段

### 操作

- 新增标签
- 编辑标签
- 删除标签
- 标签搜索
- 分类筛选

### 当前数据结构的重要约束

目前文章标签存储方式为逗号分隔的文本，并非文章与标签通过标签 ID 建立关联。

因此：

1. 当前版本不得假设文章标签与标签表存在完整的 ID 关联。
2. 删除标签记录时，只删除标签记录本身。
3. 不得自动声称会清理文章中已有的标签文本。
4. 删除确认框必须明确说明该操作的影响。
5. 如果无法准确统计关联文章数量，则不展示虚假的关联数量。
6. 不得为了展示关联数量而使用不可靠的字符串模糊匹配结果。
7. 后续可以独立安排文章标签关系表迁移。

### 删除交互

点击删除：

- 打开确认弹窗。
- 显示标签名称。
- 显示所属分类。
- 说明删除不可撤销。
- 说明文章中已有的标签文本不会自动清除。
- 提供取消和确认删除按钮。

确认删除后：

- 按钮进入加载状态。
- 禁止重复提交。
- 删除成功后关闭弹窗并刷新列表。
- 显示成功提示。
- 删除失败时保留当前页面和操作上下文，提示失败原因。

# 六、后端开发规范

## 6.1 分层结构

遵循项目现有分层结构，通常包括：

- Controller：接收请求、参数校验、返回响应。
- Service：业务逻辑处理。
- Mapper：数据库访问。
- Entity：数据库实体。
- DTO：请求参数对象。
- VO：页面展示对象。
- Config：配置类。
- Common：公共响应、工具类和常量。

不要将复杂业务逻辑直接写在 Controller 中。

## 6.2 接口规范

后台写操作统一使用 POST 请求。

查询接口可以根据项目现有规范使用 GET 或 POST。

接口应具备：

- 参数校验
- 登录校验
- 权限校验
- 统一响应结构
- 异常处理
- 业务错误提示

建议统一响应结构：

- code
- message
- data

实际字段命名应遵循项目当前的统一响应规范，不要在已有项目中重复创建另一套响应格式。

## 6.3 权限要求

- 普通访客不能访问后台。
- 普通用户不能执行管理员操作。
- 管理员才能访问后台管理功能。
- 所有写操作必须在服务端检查权限。
- 不能仅依靠前端隐藏按钮控制权限。
- 修改用户角色、修改密码等敏感操作必须再次校验。

## 6.4 安全要求

- 密码必须使用安全哈希方式存储。
- 防止 SQL 注入。
- 防止 XSS。
- 防止越权访问。
- 文件上传限制文件类型和大小。
- 防止重复提交。
- 登录接口应具备基础防暴力尝试措施。
- 不在接口响应中暴露异常堆栈和敏感配置。

这是整个项目非常重要的执行约束。

## 9.1 执行前必须检查

每次开发新模块前：

1. 阅读本需求文档。

6. 检查已有页面和接口。

## 9.2 开发过程中

- 一次只执行一个明确的开发阶段。
- 不要擅自修改无关模块。
- 不要删除已有业务代码。
- 不要用假数据代替数据库查询。
- 不要为了页面好看而增加没有实际意义的按钮。
- 不要创建没有后端功能支持的交互。
- 不要在未确认数据库结构前执行破坏性 SQL。
- 新增代码应遵循项目现有命名规范。
- 关键业务逻辑需要有必要注释。

## 9.3 每个模块完成后

Cursor 必须输出：

1. 本次完成的功能。
2. 新增的文件。
3. 修改的文件。
4. 数据库是否发生变化。
5. 新增或修改的接口。
6. 权限校验情况。
7. 自测结果。
8. 尚未完成的问题。
9. 对其他模块的影响。

## 9.4 禁止事项

未经明确要求，不得：

- 更换项目技术栈。
- 大规模重构项目。
- 删除已有数据库表。
- 清空已有业务数据。
- 修改现有登录体系。
- 修改现有 URL 路由规则。
- 引入复杂权限框架。
- 引入多租户架构。
- 增加 AI Agent 工作台。
- 增加任务管理、企业审批等与当前定位无关的模块。
- 擅自增加日记私密权限体系。
- 将尚未开发的功能描述为已经实现。
